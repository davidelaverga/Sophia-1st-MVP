# ADR-001 · Configuration Validation & Dev Mode

## Status
Accepted — 2025-01-07

## Context
The Sophia backend relies on numerous external services: Supabase for persistence, Mistral and Inworld for conversational AI, Phoenix/Gemini for emotion analysis, plus optional fallbacks via OpenAI or Anthropic. Historically, missing environment variables caused non-deterministic failures at runtime (e.g., Supabase inserts throwing connection errors, Voxtral requests failing silently, or consent checks bypassing due to unset API keys). Developers also needed a lightweight way to run the backend locally without provisioning every external API on day one.

Key requirements emerged:
- Fail fast when core infrastructure credentials are absent, so deployments do not reach production in a broken state.
- Allow local/staging work without setting all API keys while clearly communicating degraded functionality.
- Reuse a single Supabase client at startup to avoid connection churn and timeouts.

## Decision
1. **Centralize validation** using `validate_settings` in `app/config_validation.py`. The validator runs during import in `main.py` and terminates the process with a descriptive error if critical settings (e.g., `SUPABASE_URL`, `SUPABASE_KEY`, production `API_KEYS`, production AI keys) are missing or malformed. It also verifies that `APP_ENV` is one of `development`, `staging`, or `production`.
2. **Provide a development fallback**: In non-production environments the validator logs warnings instead of aborting when optional AI keys are absent. Service modules use mock behaviors (e.g., returning neutral emotions, mock MP3s) so developers can iterate without full credentials.
3. **Initialize Supabase once** via `init_supabase(settings)` during startup. The helper validates that the fallback user ID is never the zero UUID and raises if Supabase credentials are absent, eliminating per-request initialization.
4. **Document environment expectations** in `.env.template` and reference it from `README.md`. The template enumerates every variable with comments so onboarding and CI pipelines remain consistent.

## Alternatives Considered
- **Lazy validation:** Defer checks until a dependency is first used. Rejected because partial failures produce inconsistent behavior (e.g., first insert works, second fails) and complicate debugging.
- **Separate dev configuration:** Maintain a dedicated `settings_dev.py`. Rejected to avoid config drift and duplication; environment variables remain the single source of truth.
- **Soft warnings only:** Continue logging warnings without aborting. Rejected because production deployments could slip into service with missing credentials, violating acceptance criteria.

## Consequences
- Deployments fail fast when critical configuration is missing, improving confidence in production rollouts.
- Local development retains flexibility: warnings highlight missing integrations, but the app still boots for feature work if `APP_ENV` is not `production`.
- Supabase connections and defaults are consistent; APIs no longer write zero UUIDs or create clients repeatedly, reducing latency and data cleanliness issues.
- The README now guides contributors through configuration, tying together `.env.template`, `SECURITY.md`, and `observability.md`.

## Related Work
- `app/config_validation.py`: validation logic and environment guardrails.
- `app/services/supabase.py`: centralized client initialization and non-zero user ID enforcement.
- `.env.template`: canonical list of environment variables.
- `README.md`: quick start instructions referencing the template and documentation set.
